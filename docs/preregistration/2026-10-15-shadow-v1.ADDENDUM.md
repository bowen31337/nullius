# Addendum 1 to the forward VST shadow v1 pre-registration

- **Filed:** 2026-10-15 (14:xx UTC on 2026-10-14). No shadow book has been traded yet, and the forward window has not started. `2026-10-15-shadow-v1.md` is unchanged, and its `.sha256` still verifies.
- **What changes:** only the timing of the book build and of the switch.
- **What does not change:** the nodes, the weights, the costs, the cadence of decision dates, and the primary outcome and its pass rule.

## The defect
Four of the five nodes read the `metrics` stream (open-interest metrics). Binance publishes day D's daily metrics file at about **07:30 UTC on D+1**: BTCUSDT's 2026-10-12 file at 07:56 UTC, and its 2026-10-13 file at 07:24 UTC.

The registered build time was 02:30 UTC on D+1. At that hour the bars and the perp closes for D exist, but the metrics for D do not. Under the old rule, `shadow-book` would have picked decision date D and scored it with D's metrics missing. The hold rule never rebuilds a book once its `book_id` is written, so that incomplete book would have been traded for all 14 days.

## The fix
- **Build time:** the timer (`nullius-shadow.timer`) moves to **09:30 UTC** on D+1.
- **Guard:** `shadow-book` gets `--require-stream metrics`, which `shadow_daily.sh` passes when `SHADOW_METRICS=1`. The decision date then also needs BTCUSDT's metrics for that date. If the file is late even at 09:30, the previous book is held, and D's book is built the next day. The incomplete book is never written.
- **First traded slot:** a book built at 09:30 UTC on D+1 is first traded in the **12:05 UTC slot on D+1**, not 04:05. The lag behind the research convention (enter at D's close) is now about 1.5 days instead of about 1 day. It is disclosed here and not corrected for.

## Window, restated
- **Switch:** expected at 2026-10-20 about 09:30 UTC. That is when the shadow job runs `shadow_switch.sh`.
- **Window:** 90 calendar days, from the first shadow slot (**2026-10-20 12:05 UTC**) to **2027-01-18 12:05 UTC**.
- **Decision dates:** about 7, from 2026-10-19 to 2027-01-04, as before.

Primary P is a daily close-to-close accounting from the history books. It is unaffected, except that on each day d it uses the book in force on d, from the history file's own timestamps.

## Also fixed (no effect on the book's values)
Backfill fetches now retry transport failures and time out stalled sockets (`24d2a7f`). A single dropped connection had ended the 460-day metrics bootstrap partway through.

# Addendum 2: deterministic row order in the signal sandbox

- **Filed:** 2026-10-15, about 01:00 UTC. No shadow book has been written to `history/` yet, and the forward window has not started. `2026-10-15-shadow-v1.md` is unchanged, and its `.sha256` still verifies.
- **What changes:** the sandbox's signal runs become reproducible.
- **What does not change:** the nodes, their stored code, the weights rule, the costs, the cadence and the primary outcome.

## The defect
Polars seeds its hash function from the operating system's random source in every process, and the pinned thread and hash-seed variables do not cover it. So inside the signal sandbox, `unique`, `group_by` and `join` without `maintain_order` returned rows in a different order in each process.

Row order reaches a score through order-dependent float sums. One re-evaluated research node's ic_mean varied by about 0.1% between runs. Two symbols tied exactly in one run and split in another, because a group mean differed in its last bit. All five shadow nodes use these operations. Their books would therefore have been one random draw out of several near-identical books: the traded book and the scored book are the same stored file, but an independent rebuild could differ slightly.

## The fix
Before agent code runs, the sandbox child (`orchestrator/_sandbox_child.py`) now forces order preservation on polars' hash-ordered operations:
- `unique`, `group_by`, `partition_by`, `pivot` and `mode` get `maintain_order=True`;
- `join` gets `maintain_order="left_right"`.

This changes only the order of the rows, never which rows or what they hold. The same code and data now give the same book in every run. The gVisor runtime root was re-provisioned with the new child, and the fix landed before the first shadow book (decision date 2026-10-19).

Every forward book is built under the fixed sandbox. Research results recorded before the fix (M2 and earlier) were single draws from the old sandbox and stand as recorded; their variation is far below every decision threshold.

# Addendum 3: a non-ASCII symbol's metrics, and snapshot pruning

- **Filed:** 2026-10-15, about 09:50 UTC. The forward window has not started. `history/` holds one book, decision date 2026-10-05, before the window; it was built after both fixes below and is not scored. `2026-10-15-shadow-v1.md` is unchanged, and its `.sha256` still verifies.
- **What changes:** one lake symbol, `牛来USDT`, now has `metrics` like every other symbol.
- **What does not change:** the nodes, their stored code, the weights rule, the costs, the cadence and the primary outcome.

## The defects
1. **Metrics for a non-ASCII symbol.** Binance lists `牛来USDT` (in the shadow universe since 2026-09-09). The archive fetch sent its URL unencoded, and `http.client` can only send ASCII, so the fetch raised `UnicodeEncodeError`. No per-day handler caught it, so each metrics run died at that symbol. The symbols processed before it were complete. `牛来USDT` itself had bars, funding and futbars but never any metrics. `shadow_daily.sh` read the exit status as "the archive has not published yet" and carried on.
2. **Pruning a sealed snapshot.** `lake-seal` leaves every snapshot directory read-only, so `rm -rf` could not remove an old snapshot. The first prune that had something to remove (the 09:30 UTC run on 2026-10-15) failed, and the book step never ran.

## The fix
- The archive fetch percent-encodes its URL (`bars_backfill.urllib_archive_fetch`). An ASCII URL is sent unchanged. `牛来USDT`'s metrics for 2026-09-09..2026-10-14 (36 days) were backfilled.
- The prune step makes a snapshot writable before removing it.

`牛来USDT` is not a BingX VST contract, so it never takes a position. But the signal runs over the whole lake universe, and only its output is restricted to BingX before z-scoring. Agent code that ranks across the whole universe could therefore move other symbols' raw scores slightly when this symbol's metrics appear. That is why this is recorded here. Every book in the window is built from the complete lake.

# Addendum 6: the book file is byte-reproducible

- **Filed:** 2026-10-16, about 00:40 UTC. The forward window has not started. `history/` still holds only the pre-window 2026-10-05 book, which is not scored. `2026-10-15-shadow-v1.md` is unchanged, and its `.sha256` still verifies.
- **What changes:** only the order of the symbols in the written book file.
- **What does not change:** the nodes, their stored code, the weights rule, the costs, the cadence and the primary outcome. Every value in the shadow book is unchanged (checked below).

## The defect
Addendum 5's rebuild matched the history book in every value but not in its bytes. `shadow-book` combines the nodes' weights over a Python `set` of symbols, which iterates in each process's own string-hash order. So the symbol order in `weights` and `decay_horizon_seconds` changed from build to build, and the combined book's gross was summed in that same order, so its last bit could have changed too.

## The fix
`orchestrator/shadow.py` combines the symbols in sorted order, sums the gross with `math.fsum` (exactly rounded, so order cannot move it), and writes `weights` sorted by the BingX symbol. The same snapshot, contracts, ticker and nodes now give the same file, byte for byte.

## Check
The 2026-10-05 book was rebuilt twice from snapshot `2026-10-15T09:39:13Z_6305fb`, under `PYTHONHASHSEED` 5 and 99. The two files are byte-identical (sha256 `19bffb378eea…`), and every weight, the `book_id` and every other field equal the history book's. The history file itself is kept as written.
