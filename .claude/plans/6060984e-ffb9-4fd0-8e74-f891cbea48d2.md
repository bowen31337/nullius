# Feature 51 — stamp every feature row with `computed_as_of` at write time

## What the spec asks for

app_spec.xml, category "Point-in-Time Feature Store":

> **51** (depends_on 48) — System stamps every feature row with `computed_as_of` at write time
> **52** (depends_on 51) — System returns only rows whose `computed_as_of` is at or before the query time, so a point-in-time read cannot see a later computation

docs/nullius-tech-architecture.md §4.4:

> **Point-in-time correct by construction:** every row carries `computed_as_of`, and a query at `t` may only return rows with `computed_as_of <= t`.

**This task is 51 only.** The scope is the *write* half: stamping at write time. Feature 52 (the `<= t` read filter) is a separate task that depends on this one; I will build the row layer 52 needs, but not the filter.

## What exists today (and what doesn't)

The category is well developed — 48 (keying), 53 (versioned rows), 55/56/57/58 (the four metric families) are all landed and green. But **there is no row layer at all**. `packages/feature-store/src/feature_store/` has no module that handles rows; `FeatureRecord.payload` is opaque `bytes` and every persistence module encodes *one aggregate value per record* (a `CorrelationResult`, `DispersionResult`, `RegimeLabels`, …) as a JSON envelope.

`store.py:16-18` says this explicitly, and it is the design note this task fulfills:

> Row-level point-in-time stamping (`computed_as_of`, features 51/52) likewise lives in the payload layer those features add.

`keys.py:22-23` agrees. So 51 = **build the payload/row layer** and stamp it. Feature 49 (lazy Parquet materialisation) has *not* landed — no parquet module, no `cache_hit`, no lake-rooted store — so there is no existing row container to stamp into. I am creating it.

## Design

### New module: `packages/feature-store/src/feature_store/rows.py`

The row layer, stdlib-only (matching `keys.py` / `store.py`, so the replay path stays import-safe).

**`FeatureRow`** — one row of a feature's payload, carrying its stamp:

- `computed_as_of: datetime` — the stamp. **Required, timezone-aware, UTC.** Naive datetimes are refused: §4.4 makes `computed_as_of` the thing a `<= t` comparison is performed on, and a naive datetime compared against an aware one raises `TypeError` at the comparison, i.e. deep inside feature 52's query rather than at the write that could name its offset. Rejecting at construction puts the failure on the writer.
- `values: Mapping[str, object]` — the row's named values (the columns). Kept to JSON-representable scalars; identity is still the key's (feature 48's contract — the key is the address, the payload is interpretation, and this module is the interpretation layer feature 48 deferred to).
- Frozen, validated at construction. A stable iteration/serialisation order via sorted keys, matching the determinism discipline of `keys()` / `versions()` / `records()`.

**`stamp_rows(values, *, computed_as_of=None, clock=None)`** — the write-time stamping entrypoint:

- Assigns **one** `computed_as_of` to every row in the batch, taken **once**, at the top of the call. Read the wall clock once per write, not once per row: a batch straddling a clock tick would otherwise carry two stamps and a later `<= t` query could return *part* of a batch — the exact silent leakage §4.4 exists to prevent.
- `computed_as_of` may be passed explicitly (the caller that knows when the computation happened); otherwise `clock()` supplies it, defaulting to `datetime.now(UTC)`.
- `clock` is an injected zero-argument callable, so tests and the deterministic replay path never have to monkeypatch a global. This matches the codebase's convention (cf. `universe/store.py`, `snapshot/_recomputation.py::_now`) and the explicit "never reads the wall clock" discipline `contract/resolution.py` argues for at length.
- Returns `tuple[FeatureRow, ...]` — immutable and ordered.

**`encode_rows` / `decode_rows`** — the payload bridge, so the row layer plugs into the existing opaque-`bytes` seam rather than beside it:

- Deterministic JSON envelope, sorted keys, no incidental whitespace — the same discipline `dispersion_persistence._envelope` / `persistence.encode_*` already follow ("the replay path compares payloads").
- `computed_as_of` serialises as ISO-8601 with an explicit offset (`2026-09-19T23:14:48+00:00`), so the stamp round-trips losslessly and is legible in a payload dump.
- The decoder reconstructs aware-UTC datetimes and **revalidates** through `FeatureRow.__post_init__`, so a payload that wandered in from disk cannot smuggle in a naive stamp.
- Decode refuses a payload whose envelope names a different feature or a later version — mirroring `dispersion_persistence._require_feature`.

### Wiring: `packages/feature-store/src/feature_store/__init__.py`

- Re-export `FeatureRow`, `stamp_rows`, `encode_rows`, `decode_rows`, and the error type; add to `__all__`.
- **No new `@register` component.** This was my one real judgement call, and I want to flag it:

  Every registered component in this member is an *orchestration service* — something with `persist`/`load` that owns panel assembly and store binding (`RegimeService`, `DispersionService`, `VolatilityService`, `RegimeLabelerService`). Row stamping is not that; it is a pure function over rows, and the payload layer of the store's own contract. Registering a `"point-in-time-rows"` component would put a stateless function in the composition root where nothing composes it, and would add a name to `app.order` that no other feature reads. Feature 54 (the most recent comparable non-service layer) registered nothing either. So the public surface is the module plus the package re-exports, and plugins stay purely additive.
- Keep `src/app/modules/feature-store/__init__.py` (the app-package seat) unchanged, since no new component is named. It remains the seat's job to expose *components*, and there is no new one.

### Tests: `tests/feature-store/test_rows.py`

New file, mirroring the existing suites' style (module docstring tying each test to the spec sentence, `pytest.raises` on the exact message match, helpers at the top):

- one stamp per batch, applied to every row — the core of "stamps every feature row at write time";
- **all rows in one batch carry the identical stamp**, asserted with a `clock` that advances per call (this is the clock-tick test: a per-row clock read is the bug);
- the stamp is written *at write time*, not read later — a clock that returns a different value on every call yields the first value, and re-reading a row returns the stored stamp;
- an explicit `computed_as_of` is honoured verbatim (overrides the clock, and the clock is not consulted);
- validation: naive datetime refused, non-UTC aware datetime is normalised to UTC (so `<= t` comparisons are well-defined across offsets), non-datetime refused, non-mapping values refused;
- rows are frozen; iteration/serialisation order is deterministic and insertion-independent;
- `encode`/`decode` round-trips losslessly, is byte-deterministic across calls, and produces byte-identical payload for rows built in different insertion orders;
- decode revalidates: a hand-built payload carrying a naive stamp is refused;
- decode refuses a wrong feature name / wrong version;
- the stamped payload travels through the real `FeatureStore`/`FeatureRecord` seam end to end (put → get → decode → stamps intact), proving the layer plugs into feature 48's contract rather than sitting beside it.

### Docs

- `packages/feature-store/README.md` — a short "Feature 51 — row-level `computed_as_of` stamping" section: what the stamp is, why the clock is read once per batch, and that the `<= t` filter is feature 52's (not implemented here). The README currently documents every landed feature in the category and ends by noting "point-in-time row filters (51/52) layer on top of this seam" — that closing line needs updating to reflect that 51 has landed.
- Module docstrings in `store.py` and `keys.py` currently say stamping "lives in the payload layer those features add" — a forward reference that becomes stale once the layer exists. I will point those at `rows.py`.

## What I am deliberately not doing

- **Not implementing feature 52's filter.** No `as_of=` query parameter, no `rows_as_of(t)`. That is a separate task, and adding half of it here would mean the acceptance gate for 51 is passing on 52's work.
- **Not touching `store.py`'s `put`/`get` signature or `FeatureRecord`'s fields.** Feature 48's contract is landed and green, and every persistence module depends on it. The stamp belongs in the payload, which is exactly where feature 48's docstring says it belongs.
- **No new shared-file edits.** No registry, router, app factory, middleware, settings, or migration changes. The member is already declared by `packages/*` and already scanned.
- **No Parquet.** Feature 49 (lazy materialisation) has not landed; when it does, it serialises `FeatureRow`s, and the stamp travels with them.

## Risk

Low. The change is one new stdlib-only module, additive re-exports, two docstring corrections, a README section, and a new test file. It does not modify any landed contract, any shared file, or any existing behaviour. The one thing worth stating plainly: because feature 49 never landed, I am *choosing* the row representation (dataclass over columnar arrays) rather than adopting an existing one — so 49 and 52, when they land, will find the seam I built rather than one the spec handed me.
